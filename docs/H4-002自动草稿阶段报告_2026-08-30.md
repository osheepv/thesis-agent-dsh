# 一、轮子优先评审（本任务第一个产物）

按任务卡第 5 节要求，本阶段第一个产物是轮子评审。评审在动手写代码前完成，结论是**不新增依赖**。

## 1.1 需求拆解

要解决的问题可以拆成四件独立的事：

1. **编辑面内容采集**：从 DOM 表单/textarea 读取结构化 JSON 快照。
2. **延迟写入**：停顿约一秒后发一次请求，连续输入只发最后一次。
3. **乱序与并发保护**：多标签页、pagehide、旧请求迟到时不能让旧内容覆盖新内容。
4. **持久化与隔离**：进程重启可恢复，按任务/租户/作者隔离。

这四件事分别由浏览器原生能力、已验证的 revision 契约、以及项目已有的 SQLite 仓储覆盖。

## 1.2 候选轮子评估

| 候选 | 用途 | 评估 | 结论 |
|---|---|---|---|
| **Yjs** | CRDT 多人实时协同 | 需要常驻 WebSocket/信令服务与持久化 provider；解决的是“多人同时编辑同一文档”，而本产品是单作者、单机、本地 FastAPI。引入它会同时引入协作语义（本任务卡第 3 节明确排除多人协作）。 | **不引入** |
| **Automerge** | CRDT 文档合并 | 同上。JavaScript/Python 双端都要引入新的存储格式，且需要额外合并层；与“正式产物是不可变版本 + 作者审批”的模型不兼容。 | **不引入** |
| **Dexie / localForage** | 浏览器端 IndexedDB 封装 | 只能解决“本机离线暂存”。任务卡第 5 节明确禁止把 IndexedDB/localStorage 作为正式真相源。原生 `localStorage` 已用于 Job 预算，IndexedDB 封装库无收益。 | **不引入** |
| **Redis** | 服务端草稿缓存 | 单机本地部署场景；项目当前只有 SQLite 持久化，引入 Redis 会增加一个必须运维的进程，且不能提供比 SQLite 更强的持久化保证。 | **不引入** |
| **SQLAlchemy ORM** | 持久化 | 已在运行时依赖中（`SQLAlchemy==2.0.41`）。但本产品现有仓储（SectionDraftRegistry、JobRegistry、ArtifactRegistry 等）统一使用 `sqlite3` + 显式 SQL + `RLock`。为了一致性，草稿仓储沿用相同风格，不混用第二套持久化范式。 | **复用，不新增** |
| **Pydantic v2** | 请求/响应校验 | 已在依赖中（`pydantic==2.11.4`），`WorkspaceState` 已用其 `extra="forbid"` 做严格契约。草稿保存请求沿用同样手法。 | **复用，不新增** |
| **FastAPI** | 路由 | 已在依赖中。新增四个草稿路由沿用现有 `writer_console` 风格。 | **复用，不新增** |

## 1.3 浏览器原生能力评估

| 能力 | 是否满足 | 说明 |
|---|---|---|
| `input` / `change` / `keyup` 事件 | 满足 | 足以在每次击键后触发防抖调度。 |
| `setTimeout` / `clearTimeout` | 满足 | 800–1200ms 防抖，与 H4-001R 已验证的 300ms 工作区防抖同源。 |
| `fetch(..., {keepalive: true})` | 满足 | H4-001R 已用它做 pagehide 末次保存，并在真实浏览器中验证。 |
| `pagehide` 事件 | 满足 | 同上。 |
| `AbortController` | 满足 | 需要超时控制时可用；本阶段保存请求走串行队列，暂不需要主动取消。 |
| `structuredClone` / `JSON` | 满足 | 草稿内容是结构化 JSON 快照，不需要二进制 diff。 |

无一项需要外部库补足。

## 1.4 关键设计结论

- **复用 H4-001R 已证明的单调 revision + 身份世代隔离思想**，而不是另造一套并发模型。区别只是 revision 的作用域从“整个工作区”下沉到“每个 draft_key”。
- **使用完整 JSON 快照 + 服务端重算内容哈希**，不做增量 Patch。草稿体积上限 512 KiB，快照的序列化成本远低于维护增量合并逻辑的正确性成本。
- **只在服务端判定冲突**。客户端不做“谁最后写谁赢”，也不做时间戳比较。
- **不新增任何依赖**。任务卡第 5 节明确指出：“当前依赖足够时，‘不新增依赖’也是合格的轮子优先结论。”

## 1.5 如果未来需要新增依赖

只有当真实 POC 证明现有栈无法满足需求时才允许。新增前必须记录：许可证、维护状态、Windows 与 Python 3.13 兼容性、安装体积、数据是否外发、版本固定方式、替换方案、契约测试。禁止为了使用轮子反过来重构产品架构。

## 2.2 草稿域模型与 API

- 状态：`ACTIVE`、`STALE`、`SUBMITTED`、`DISCARDED`。墓碑保留更高 revision，旧的在途保存不能复活已提交/已丢弃草稿。
- 隔离键：租户 + 作者 + 任务 + `draft_key`；评审者/只读角色不能保存作者草稿。
- 上限：单草稿 512 KiB，同作者/任务限制数量，`draft_key`、字段长度和 JavaScript 安全整数 revision 均在服务端校验。
- API：列表、详情、`PUT` 保存和 `POST .../discard`。列表/恢复摘要仅返回元数据，只有授权的详情读取才返回正文。
- 并发：incoming revision 必须单调。旧版本拒绝；同 revision 不同内容明确冲突；同内容重放幂等。

## 2.3 真实编辑面

1. 分节修订：每个分节独立 `draft_key`，切换前 flush，正式修订成功后标记 `SUBMITTED`。
2. 项目记忆：结构化表单恢复，正式版本仍必须作者审批后才能进入 Agent 上下文。
3. 研究协议：协议名称、问题、步骤、分析计划、必须产物等字段恢复。
4. 论证图：动态论断行、角色、父子键和证据需求一并恢复。

`RESULT_RECORD_FORM` 仅是后端类型预留，本阶段没有宣称已接入结果登记表单。

# 三、交互、恢复与安全边界

- 输入停顿 1 秒后保存；同一草稿串行化常规保存，pagehide 使用更高预留 revision + `keepalive`。
- 多页面不做实时合并或 CRDT。检测冲突后停止自动重试，由作者选择“使用服务端版”、“确认使用本地版”或“两者都保留”。
- 没有把 IndexedDB/localStorage 当草稿正文真相源。断网时内容只留在当前页并可重试；成功写入服务端后才承诺跨刷新/进程恢复。
- 草稿不推进 FSM、不创建正式产物、不进入 Agent 上下文、不触发模型调用。
- 正式提交先 flush 并携带 `autosave_draft_key + autosave_revision`。正式操作成功才转 `SUBMITTED`；校验/业务失败保留 `ACTIVE`。
- 上游正式版本变化会将相关草稿标记 `STALE`，作者必须基于新版重建后才能提交。

## 4.2 真实浏览器与进程重启

使用隔离临时 SQLite 和静态 UI 进行了真实 Playwright 验收，DeepSeek 显式禁用，没有付费模型调用。已验证：

- 项目记忆输入保存到 v3，刷新后字段、展开项和状态原样恢复。
- 项目记忆正式提交后，页面无需刷新即将“未提交草稿”从 1 更新为 0，正式版本进入 `WAITING_APPROVAL`。
- 研究协议保存后停止 FastAPI，以同一数据库重启后刷新，字段、revision、展开项和“未提交草稿 1”均恢复。
- 验收暴露出两个真问题：初始默认表单会在 pagehide 生成幽灵草稿；正式提交后重置表单会被 pagehide 误当新编辑。`42d8590` 建立“缺失草稿也是已加载基线”与“提交/丢弃后重置快照为新基线”的契约，并增加确定性回归。
- 关键流程控制台0 Error；资源请求均成功。
