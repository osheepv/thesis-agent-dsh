### 2.2 标杆方案详述

> 每家标杆逐一展开；每段区分「已核实的事实」与「推断/假设」。

#### 2.2.1 B1 - DeepSeek-Harness (DSH)

| 维度 | 内容 | 置信度 |
| --- | --- | --- |
| 产品定位 | 开源 Agent harness——把"模型"变成"有手（工具/沙箱/会话）的 Agent"；内核是插件编排框架 Cordis | 已核实 |
| 目标用户 | 需要自建 Agent 运行时、且不绑定一体化 IDE 的开发者/团队 | 已核实 |
| 核心能力 | 模型适配、工具、技能、会话、沙箱、存储、工作流、子代理、审批策略、Web UI，全部为插件 | 已核实 |
| 架构特点 | 插件是唯一主体（everything is a plugin）；Cordis 仅负责加载/卸载/依赖关系，不含 Agent 能力；"seam"-三元组（Service Definition / Provider / Consumer）解耦可替换实现 | 已核实（来源：官方架构解读） |
| 部署形态 | 自托管，`npx @deepseek-ai/dsh web` 一键起，或源码 `pnpm` 构建 | 已核实 |
| 集成方式 | 配置层组合（Profile / Bundle / cordis.patch.yml）；可为模型/工具/UI/存储接第三方插件；可作子 agent 调用其它 harness | 已核实 |
| 定价模式 | MIT 开源免费；模型推理自备 key（配 DeepSeek V4 Pro/Flash 或任意 OpenAI 兼容端点，经 `DEEPSEEK_BASE_URL` 切换） | 已核实 |
| 优势 | 高度可组合、可裁剪能力面；append-only 会话日志，全程可追溯；配置层替换能力无需改源码 | 已核实 + 归纳 |
| 局限 | 开发者预览版，官方明确"将有兼容性破坏变更"；无模型/无 key/无 provider，需自备；社区 15k stars 主要沉淀在演示层 | 已核实（来源：官方发布说明） |
| 对本项目的参考价值 | **直接支撑"仅依赖不 fork"命题**——DSH 本身就是插件化、配置组合型的，天然支持"以依赖方式引用 + 上层自己编排"，无需 fork 改主体 | 推断 |

#### 2.2.2 B2 - LangGraph（有向图状态机编排）

| 维度 | 内容 | 置信度 |
| --- | --- | --- |
| 产品定位 | LangChain 官方的有状态 Agent 工作流编排框架；2025-10 达 1.0，成为 LangChain 默认运行时 | 已核实 |
| 目标用户 | 需要图式状态机、长时运行、可恢复、可审计 Agent 流程的团队 | 已核实 |
| 核心能力 | 有向图节点/条件边；typed state 贯穿；checkpointing（Postgres/SQLite/Redis/Mongo）；原生 HITL interrupt；streaming；时间旅行调试 | 已核实 |
| 架构特点 | 把 Agent 建模为显式图状态机，状态是类型化字典，边是显式条件路由 | 已核实 |
| 部署形态 | 自托管（Python）；配套 LangSmith 商业观察平台 | 已核实 |
| 集成方式 | 通过 Python SDK 嵌入自建服务；checkpointer 接任意持久化后端 | 已核实 |
| 定价模式 | 核心 MIT 开源；LangSmith/云可选付费 | 已核实 |
| 优势 | 显式状态、可控、可恢复（失败从 checkpoint 续跑而非重来）、可审计（checkpoint 历史=完整审计链）；HITL 是一等公民 | 已核实 + 归纳 |
| 局限 | 冗长（同功能比 CrewAI 多写约 4 倍行数）；学习曲线陡（评估案例称"吃掉两个 sprint"）；状态 schema 迁移需人工管理 | 已核实（来源：多篇生产实践对比） |
| 对本项目的参考价值 | **是"自研 FSM 编排"的最佳业界对标**——证明"显式状态机编排"比"隐式 LLM 控制循环"更可控、可恢复、可审计 | 推断 |

| 维度 | 内容 | 置信度 |

| 架构特点 | 模板驱动（word 内嵌 Jinja2 标签）；OOXML 比较采用"用户上传文档 XML 标签 vs 标准模板 XML 标签"比对法（PaperFormatDetection） | 已核实 |
| 部署形态 | 纯 Python 库，自托管；跨平台；无需装 Word | 已核实 |
| 集成方式 | pip 安装，render→save 两行核心；校验走 CLI / pytest 插件 / CI | 已核实 |
| 定价模式 | MIT / BSD 开源 | 已核实 |
| 优势 | 保留原格式、所见即所得、开发高效；openxml-audit 可捕获"会打不开/被 Word 修复"的损坏输出 | 已核实 |
| 局限 | docxtpl 不能动态创建全新结构（依赖模板）；openxml-audit 官方明示"python-docx 有 12+ 损坏问题、docxtpl 有 7+"；模板校验规则库需自建 | 已核实（来源：pypi）+ 推断 |
| 对本项目的参考价值 | **模板解析→生成（docxtpl）→校验（openxml-audit/模板 XML 比对）是最贴合"按用户自定义 Word 模板导出合规 docx"的方案**；高校场景已有 PaperFormatDetection 类先例，用 OpenXML 比对模板实现格式检测 | 推断 |

## 3. 对比：对比矩阵与加权评分

> **四段式「对比」段**。在 §2 的事实基础上建立对比矩阵，赋予权重并打分。此处的"对比对象"是三个待选编排范式（O1/O2/O3），因为本项目的核心设计决策是"编排层选哪种范式"。

### 3.1 对比矩阵

> **每行权重之和 = 1.00**。评估维度与权重针对"学位论文全流程 Agent 的编排层选型"设定。

| 评估维度 | 权重 | 权重理由 | O1 纯 Prompt 编排 | O2 自研 FSM 编排 | O3 状态机 + 人工网关 |
| --- | --- | --- | --- | --- | --- |
| 场景契合度 | 0.30 | 本项目是 10 环 + 本硕博差异路由 + 回退的状态机业务底座，编排范式必须能表达回退/条件分支/环形迭代 | 1 | 5 | 5 |
| 技术成熟度 | 0.20 | 需有生产级先例、可依赖成熟组件（LangGraph 为标杆） | 3 | 4 | 4 |
| 集成难度（反向） | 0.15 | 越低越好；DSH 需作底层依赖被引用，编排层宜自研轻量或复用成熟框架 | 5 | 3 | 2 |
| 成本（反向） | 0.15 | 自研/第三方/人工审核的开发与运维成本；纯 prompt 最低但质量与可恢复性弱 | 5 | 4 | 3 |
| 合规可控性 | 0.20 | 学位论文涉及学术红线，需可回退、可审计、可人工把关（HITL/网关）；**合规底线是本项目硬约束** | 1 | 4 | 5 |
| **加权总分** | **1.00** | — | **2.6** | **4.15** | **4.0** |

> 说明：O1 对应"纯 prompt 编排"（B4 StructPO 类 / 经典多智能体 prompt 链）；O2 对应"自研 FSM 编排"（B2 LangGraph 范式 + DSH 底层）；O3 对应"状态机 + 人工网关"（B2 LangGraph HITL + B3 引用/评审网关）。

**评分标尺**：每项 1~5 分，1 = 严重不符合，3 = 基本满足但存在明显局限，5 = 完美契合。

**加权计算**：
- O1 = 0.30×1 + 0.20×3 + 0.15×5 + 0.15×5 + 0.20×1 = 0.30+0.60+0.75+0.75+0.20 = **2.60**
- O2 = 0.30×5 + 0.20×4 + 0.15×3 + 0.15×4 + 0.20×4 = 1.50+0.80+0.45+0.60+0.80 = **4.15**
- O3 = 0.30×5 + 0.20×4 + 0.15×2 + 0.15×3 + 0.20×5 = 1.50+0.80+0.30+0.45+1.00 = **4.05**

> 注：O2 与 O3 差距极小（4.15 vs 4.05），且 O3 的"合规可控性"更高（业界证明 HITL 是审计/监管硬要求）。**最终编排范式已由用户经中间确认 U-04 裁决**：采用"自研 FSM + 敏感环节 HITL 人工网关"组合（即 O2 骨架 + O3 增强），HITL 为必需且插桩于 4 个敏感环节（环节 2/4/8/10），其余环节全自动运行。**经中间确认 U-04 裁决**。

### 3.2 评分结论

> 基于 §3.1 加权总分，形成分层结论。每层结论引用得分作为依据。

- **优先借鉴**：`自研 FSM 编排（O2）` — 适用度评分：**4.15**，理由：场景契合度最高（5/5，能完整表达 10 环 + 回退 + 本硕博差异路由）、技术成熟度可接受（4/5，LangGraph 为对标先例）、合规可控性（4/5）。与 `_runtime_meta.md` §6.1 已冻结的"上层自研 FSM 编排层掌控流程控制权"完全一致。
- **确认采纳（HITL 增强）**：`状态机 + 人工网关（O3）` — **经中间确认 U-04 裁决采用其 HITL 增强**，插桩于 4 个敏感环节：①环节 2 新颖度评估（确认选题方向和创新点定位）②环节 4 文献综述（确认研究空白和切入角度）③环节 8 引用校验（确认无伪引、引用真实）④环节 10 最终定稿（确认整体合规、查重风险）。其余环节（选题、调研、大纲、撰写、润色、排版）全自动运行、不打断用户。不借鉴的部分：**不做全流程人工把关**（其余 6 环节保持全自动）。理由：O3 合规可控性最高（5/5），HITL 在学术红线敏感环节兜底，与 O2 骨架组合成"自研 FSM + 敏感环节人工网关"。
- **不借鉴（否决）**：`纯 Prompt 编排（O1）` — 否决理由：场景契合度 1/5（无法可靠表达回退循环与本硕博差异路由）、合规可控性 1/5（无状态持久化、跨阶段漂移、难审计、不可回退、易出伪引），无法满足"可校验、可回退、可审计"的学位论文硬约束。评分：**2.60**。即使 B4 StructPO 将工作流内化进单遍模型，其需 RL 训练、仅针对单段引言、无合规导出，**在高 stakes 学位论文全流程场景不成立**。

### 3.3 方案组合分析

> 调研发现"单一方案无法覆盖全部需求，需要组合"。

| 组合方式 | 覆盖哪些能力 | 未覆盖能力 | 组合复杂度 | 总体成本估算 |
| --- | --- | --- | --- | --- |
| O2 自研 FSM + B1 DSH（底层）+ B5 万方（数据）+ B6 docxtpl/openxml-audit（导出） | FSM 编排、LLM 运行、查新/文献/引文核验、模板 docx 导出与校验 | 学术红线需人工把关（伪引/查重/伦理）、万方付费额度 | 中 | DSH（免费但自备模型 key）+ 万方机构订阅 + 开发人力 |
| O2 自研 FSM + O3 敏感环节 HITL 人工网关（已采用） | 在"环节 2/4/8/10"敏感环节插 HITL 审核，兜底学术红线；其余 6 环节全自动 | 需构建人工审核 UI 与状态恢复 | 中 | 新增人工审核 UI + 评审人力 |
