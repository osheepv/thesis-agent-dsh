## 2. 任务目标

将跨天续作从“恢复正式任务与页签”扩展到“恢复用户尚未正式提交的写作内容”。

用户在分节、项目记忆、研究协议和论证图等编辑界面输入内容后：

- 停顿约一秒自动保存。
- 明确显示保存中、已保存、保存失败和冲突。
- 刷新页面、关闭浏览器或重启后端后可以恢复。
- 多标签页不能静默覆盖更新内容。
- 草稿不能改变FSM、正式Artifact、审批或最终DOCX。
- 用户明确提交后才创建正式新版本。
- 正式提交成功后草稿进入已提交状态，不再重复恢复。
- 上游正式版本变化时旧草稿标记过期，不能静默套用。
- 恢复摘要只返回草稿元数据，不返回正文内容。

同时完成：

- 真实采集和恢复expanded_items。
- 真实采集和恢复editor_anchor。
- 修复H4-001R复验发现的MONITOR_JOB焦点丢失。

## 3. 本任务不是什么

本任务不是：

- 一次性重写整个正文编辑器。
- 多人实时协作。
- Google Docs式OT或CRDT。
- 导师评论系统。
- H4-003学术评测集。
- H4-005统一HTTP错误码。
- H4-007 SSE。
- H4-009数据库迁移。
- Zotero或Obsidian连接器实现。
- 真实DeepSeek验收。

自动草稿是用户私有、未提交、可覆盖的工作副本；正式产物仍保持不可变版本和作者审批。

## 4. 不可妥协边界

### 4.1 草稿不能推进论文流程

保存、恢复、删除或冲突解决草稿均不得：

- 执行当前环。
- 修改phase_state。
- 创建正式Artifact或SectionDraft版本。
- 自动批准。
- 改变当前批准版本。
- 触发模型调用。
- 进入最终DOCX。

### 4.2 只有正式提交才改变正式对象

流程必须是：

    用户编辑
    → 自动保存私有草稿
    → 用户检查
    → 明确点击提交或生成待审批版本
    → 服务端核验草稿revision和base_version
    → 创建正式新版本
    → 草稿标记SUBMITTED
    → 正式版本进入既有自动Gate与HITL

### 4.3 草稿不能作为Agent批准上下文

- 未提交草稿不能进入Agent上下文。
- 未提交草稿不能被RAG当作批准证据。
- 项目记忆仍只有APPROVED版本可被Agent读取。
- 草稿内容不能因为恢复摘要或日志意外外泄。

### 4.4 冲突不能最后写入覆盖

- 每个草稿键拥有独立单调revision。
- 旧请求不能覆盖新请求。
- 同revision同内容可幂等成功。
- 同revision不同内容必须冲突。
- 多标签页冲突后由用户决定，不自动强行覆盖。

## 5. 轮子优先评审

本任务开始后的第一个产物是轮子评审，不超过半天。

必须评估：

- 现有SQLAlchemy、SQLite、Pydantic、FastAPI能力。
- 浏览器原生input/change、setTimeout、防抖、pagehide和keepalive。
- 是否需要Yjs、Automerge、Dexie、localForage、Redis或其它同步库。

当前推荐裁决：

- 单作者、单机、本地FastAPI场景不引入Yjs或Automerge。
- 不把IndexedDB或localStorage作为正式真相源。
- 不为草稿再引入Redis。
- 复用H4-001R已经验证的单调revision和身份世代隔离思想。
- 使用完整JSON快照和内容哈希，不做复杂增量Patch。
- 当前依赖足够时，“不新增依赖”也是合格的轮子优先结论。

只有真实POC证明现有栈无法满足需求，才允许增加小型依赖。新增依赖必须记录：

- 许可证。
- 当前维护状态。
- Windows与Python 3.12兼容性。
- 安装体积。
- 数据是否外发。
- 版本固定方式。
- 替换方案。
- 契约测试。

禁止为了使用轮子反过来重构产品架构。

## 6. 自动草稿领域模型

建议新增：

    backend/writing/draft_store.py

可以拆分models和store，但不要建立过多文件。

### 6.1 DraftObjectType

本任务至少支持：

- SECTION_REVISION
- PROJECT_MEMORY_FORM
- RESEARCH_PROTOCOL_FORM
- ARGUMENT_MAP_FORM

如果现有真实界面中存在稳定的大纲修订或结果登记编辑器，可增加：

- OUTLINE_REVISION
- RESULT_RECORD_FORM

如果某个界面只是占位，不得为了勾选清单创建假编辑器。应在阶段报告中如实标记“模型已预留、前端尚无真实表面”。

### 6.2 AutosaveDraft

至少包含：

- draft_id
- task_id
- tenant_id
- author_id
- object_type
- object_id
- stage_no
- base_artifact_id
- base_version
- revision
- content_json
- content_hash
- status
- stale_reason
- submitted_to_id
- created_at
- updated_at

状态：

- ACTIVE
- STALE
- SUBMITTED
- DISCARDED

### 6.3 草稿键

草稿键必须稳定、可校验、不可路径穿越。

示例：

    section-revision:section-id
    project-memory:new
    research-protocol:new
    argument-map:new

不允许把完整标题、正文或任意用户路径直接当主键。

### 6.4 作者隔离

- 草稿默认属于当前作者。
- tenant相同但不同用户不能读取彼此未提交草稿。
- reviewer和viewer不能读取、保存、删除或提交作者私有草稿。
- owner/editor只能访问自己的草稿，除非未来另行设计共享编辑。
- 认证关闭时使用固定local author身份。

### 6.5 大小限制

- 每个草稿序列化后设置明确大小上限，建议512 KiB。
- 每任务、每作者设置活动草稿数量上限。
- 超限返回稳定业务错误，不截断正文后伪装保存成功。
- 不保存文件二进制、API Key、密码或上传控件值。

## 7. revision契约

### 7.1 服务端单调规则

复用H4-001R证明过的语义，每个草稿键独立比较：

- incoming大于current：接受。
- incoming小于current：拒绝。
- incoming等于current且内容相同：幂等成功。
- incoming等于current但内容不同：冲突。
- 首次写入：接受。

比较与写入必须在同一把锁或同一事务边界内完成。

### 7.2 客户端规则

- 每个draft_key维护独立revision。
- 每次真实编辑产生比当前更高的revision。
- 防抖合并期间只发送最新快照与最高revision。
- 发送时预留revision，避免pagehide与普通保存撞版本。
- 不同身份使用不同保存世代。
- 初始化恢复和无变化重放不递增revision。

### 7.3 冲突处理

冲突时：

- 停止自动重试。
- 拉取服务端最新草稿。
- 显示本地版本、服务端版本、更新时间和base_version。
- 用户可以：
  - 使用服务端版。
  - 保留本地版并另存为冲突副本。
  - 手工合并后产生更高revision。
  - 放弃本地修改。

本阶段可使用简单双栏文本或字段级JSON预览，不要求建设完整视觉diff编辑器。

禁止自动采用最后写入者。

## 8. 持久化与存储

### 8.1 存储位置

优先放在writing领域中，与正式SectionDraft表逻辑隔离。

要求：

- 内存测试实现与SQLite实现契约一致。
- 进程重启后可恢复。
- 不把草稿塞入WorkspaceState payload。
- 不把草稿塞入Artifact payload。
- H4-009前不做破坏性数据库迁移。

### 8.2 生命周期

- create/update：单调revision。
- get/list：只返回当前作者。
- mark_stale：上游变化时保留内容并标原因。
- mark_submitted：正式提交成功后记录目标正式版本。
- discard：用户明确放弃。
- delete_task：删除任务时清理草稿。

### 8.3 上游失效

如果base_artifact_id或base_version不再是当前活动版本：

- 草稿标记STALE。
- 保留原内容。
- 禁止一键正式提交。
- 展示上游变化原因。
- 用户可基于最新正式版本创建新草稿。

不能自动把旧草稿重新解释为适用于新大纲或新证据。

## 9. API契约

建议路由：

    GET    /api/v1/console/tasks/{task_id}/autosave-drafts
    GET    /api/v1/console/tasks/{task_id}/autosave-drafts/{draft_key}
    PUT    /api/v1/console/tasks/{task_id}/autosave-drafts/{draft_key}
    POST   /api/v1/console/tasks/{task_id}/autosave-drafts/{draft_key}/discard

可以根据现有控制器风格调整HTTP动词，但语义必须保持。

### 9.1 列表响应

列表只返回元数据：

- draft_key
- object_type
- object_id
- stage_no
- base_version
- revision
- status
- updated_at
- stale_reason

列表不返回content_json。

### 9.2 详情响应

只有草稿所有者在明确请求单个草稿时返回content_json。

### 9.3 保存请求

至少包含：

- object_type
- object_id
- stage_no
- base_artifact_id
- base_version
- revision
- content

服务端重新计算content_hash，不能信任客户端hash。

### 9.4 正式提交联动

现有正式提交入口需要：

- 接收draft_key和draft_revision，或在服务端加载当前草稿。
- 核验作者、任务、object_type和base_version。
- 核验提交的revision仍是当前版本。
- 先成功创建正式版本，再mark_submitted。
- 正式提交失败时保留ACTIVE草稿。

不能先删除草稿再尝试创建正式版本。

## 10. 前端自动保存运行时

建议新增轻量模块：

    ui/js/components/autosave.js

保持现有无构建classic script架构，不引入React、Vite或状态管理框架。

### 10.1 统一接口

建议提供：

    registerDraftSurface(config)
    loadDraft(draftKey)
    scheduleDraftSave(draftKey, snapshot)
    flushDraft(draftKey)
    discardDraft(draftKey)
    markDraftSubmitted(draftKey)
    showDraftConflict(draftKey, local, remote)

业务组件只负责：

- 稳定draft_key。
- 序列化表单。
- 反序列化表单。
- 显示对象名称。
- 正式提交回调。

不要在每个表单复制防抖、revision、冲突和身份切换逻辑。

### 10.2 状态显示

每个编辑面至少显示：

- 尚未修改。
- 保存中。
- 已保存，显示时间。
- 保存失败，可重试。
- 与另一页面冲突。
- 上游已变化，需要复核。
- 已正式提交。

用稳定role=status或aria-live播报非紧急变化。错误不能只使用短暂Toast。

### 10.3 防抖

- 推荐800至1200毫秒。
- 连续输入只发送最后快照。
- 保存请求串行。
- 请求在途时再次编辑，前一次完成后发送最新快照。
- 身份切换创建新世代。
- 页面关闭时最新快照使用安全keepalive与更高revision。

### 10.4 内容序列化

- 文本按原样保存，不把HTML直接当可信内容。
- 表单保存结构化JSON。
- 文件input、密码、API Key和隐藏安全字段不得序列化。
- 恢复到DOM时使用value、textContent或安全编辑器API。
- 不使用innerHTML恢复用户输入。

## 11. 必须接入的真实界面

### 11.1 分节修订

至少支持：

- 选中分节后加载该分节草稿。
- 输入后自动保存。
- 切换分节前flush当前草稿。
- 刷新后恢复到同一分节和内容。
- 正式提交修订后草稿SUBMITTED。
- 上游大纲或批准分节变化后草稿STALE。

如果当前分节界面缺少可编辑正文输入，应在不重写完整编辑器的前提下增加最小可用textarea或contenteditable安全表面。

### 11.2 项目记忆表单

保存：

- 研究问题。
- 作者决定。
- 导师意见。
- 术语表。
- 写作风格。
- 版本说明。

生成待审批正式版本成功后草稿SUBMITTED并清空表面。

### 11.3 研究协议表单

保存当前真实输入字段。正式创建协议成功后草稿SUBMITTED。

### 11.4 论证图表单

保存：

- 图名称。
- 研究问题。
- 论断行。
- 父子关系。
- 证据需求。

动态新增/删除论断行后也要保存。恢复时必须重新生成稳定行ID和事件绑定。

### 11.5 其它重要表单

如果结果登记表单具备稳定字段，可接入同一运行时。不要保存：

- 登录表单。
- DeepSeek API Key。
- 文件上传控件。
- 删除确认。
- 临时搜索词。

## 12. expanded_items与editor_anchor

### 12.1 expanded_items

真实采集：

- 工作台中具有稳定ID的details、折叠卡和编辑器面板。
- 打开/关闭时更新WorkspaceState。
- 切换论文任务时清空上一任务专属展开项。
- 恢复时只打开当前DOM中存在且属于当前任务的ID。
- 最多30项，保持H4-001契约。

不保存随机DOM序号或依赖渲染顺序的选择器。

### 12.2 editor_anchor

建议格式：

    draft-key#selection-start:selection-end

要求：

- 长度继续受后端限制。
- 恢复前校验draft_key属于当前任务。
- 光标位置超出内容长度时安全夹取。
- 先恢复草稿内容，再恢复选择与滚动。
- 找不到对象时清空anchor，不报错阻断页面。
- 光标位置仍是UI位置，不参与正式版本或FSM。

### 12.3 保存频率

- 编辑锚点无需每次按键写服务端。
- 在blur、切换分节、显式保存、页面隐藏或固定低频防抖时更新。
- 草稿正文和工作区位置使用各自revision，不混成同一记录。

## 13. 恢复摘要联动

### 13.1 autosaved_drafts

ResumeSummary不再固定为空，返回当前作者的活动草稿元数据：

- draft_key
- object_type
- object_id
- stage_no
- base_version
- revision
- status
- updated_at
- stale_reason

绝不返回：

- content_json
- 正文片段
- 表单全文
- API Key
- 文件内容

### 13.2 capability

只有后端、API和至少四个真实编辑面全部可用时：

    draft_autosave = true

不能只建表就把能力标为true。

### 13.3 下一安全动作

可以增加：

    RESUME_DRAFT

但只在以下条件同时满足时使用：

- 没有REPAIR_REQUIRED。
- 没有活动Job。
- 没有待审批或作者决定。
- 存在与当前环直接相关的ACTIVE且非STALE草稿。

项目记忆等跨环表单草稿可以列出，但不能无条件抢占当前环唯一安全动作。

### 13.4 继续入口

点击恢复草稿：

- 选择正确任务。
- 打开正确页签。
- 加载单个草稿详情。
- 聚焦对应编辑器。
- 恢复editor_anchor。
- 不正式提交。
- 不执行模型。

## 14. MONITOR_JOB焦点跟进

Codex复验发现：

- 点击继续后曾聚焦Job卡操作按钮。
- activateWorkbenchTab异步重绘Job列表后，该按钮被替换，焦点可能掉回body。

本任务必须修复：

- MONITOR_JOB优先聚焦稳定的jobs-refresh按钮；或
- 等最终Job列表渲染完成后再聚焦新卡片。

要求：

- 键盘激活继续后焦点不掉回body。
- 异步刷新后仍有合理焦点。
- 增加Node状态流测试和真实浏览器断言。

这是H4-001R签收后的非阻断跟进，不允许扩展为整个UI响应式重构。

## 15. 身份、权限与安全

### 15.1 权限

- owner/editor只能操作自己的私有草稿。
- reviewer/viewer无权读取草稿内容。
- reviewer/viewer无权保存、丢弃或提交草稿。
- 工作区位置仍允许viewer保存，不要误伤H4-001权限。
- 正式审批权限保持原规则。

### 15.2 租户

- 所有草稿API按task tenant校验。
- draft_key不能绕过task_id读取其它任务。
- 同名draft_key在不同任务、用户中完全隔离。

### 15.3 日志

日志和审计只记录：

- task_id。
- draft_id。
- object_type。
- revision。
- 字节数。
- hash前缀。
- 结果和耗时。

不记录content_json、正文、表单全文或密钥。

### 15.4 恢复响应

恢复摘要、列表API和错误响应不能包含完整草稿内容。只有详情API在授权成功时返回。

## 16. 失败与恢复矩阵

至少验证：

| 场景 | 期望 |
|---|---|
| 普通刷新 | 草稿与保存状态恢复 |
| 后端进程重启 | SQLite草稿恢复 |
| 快速连续输入 | 只保存最新快照 |
| 普通保存与pagehide乱序 | 高revision最终保留 |
| 两标签页同revision不同内容 | 明确冲突 |
| 保存请求失败 | 内容留在编辑器并显示失败 |
| 冲突后重试 | 不循环覆盖 |
| 切换任务 | 先flush，不能串草稿 |

| 正式提交失败 | ACTIVE草稿仍在 |

| 上游版本变化 | 草稿STALE，禁止直接提交 |
| 删除任务 | 草稿全部清理 |
| viewer访问详情 | 拒绝 |
| ResumeSummary | 仅元数据，无正文 |
