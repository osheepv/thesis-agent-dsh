## R1. B01：身份切换时新用户首次保存可能丢失

**根因**：保存控制器使用全局布尔量 `workspaceSaveInFlight` / `workspaceSaveQueued`，旧身份的在途请求会占用新身份的状态，旧回包返回后只把旧世代的排队标记留在全局量上，新身份的首次保存可能既不发出也不重排。

**修复**：改为**按身份世代隔离的保存控制器**。

- 每次 `pauseWorkspacePersistence()`（登录、退出、身份切换、初始化开头）调用 `newWorkspaceSaveGeneration()` 创建新世代对象，含 `token` / `inFlight` / `queued` / `lastSnapshot`。
- `runWorkspaceSave()` 在函数入口**捕获当前世代对象**，全程只读写该对象的字段；`finally` 中仅在 `generation === workspaceSaveGeneration` 时才重排队列。
- 回包处理前先比较 `generation !== workspaceSaveGeneration`，旧世代响应直接丢弃，不修改 UI、播报、缓存或队列。
- 未采用“把 `workspaceSaveInFlight` 强行置 false”的做法（任务卡明令禁止）：旧请求的 `finally` 仍可能改错新请求的全局状态。

**额外发现并修复的设计缺陷（测试暴露）**：`workspaceRevision` 在身份切换时被归零，导致新身份发出的 revision 与旧身份仍在途的请求**撞版本**，被服务端判定为“同版本不同内容”而拒绝，新身份首次保存仍然丢失。修正为：

- 客户端 revision 计数器**只增不减**（`adoptWorkspaceRevision` 只做 `max`）；
- `runWorkspaceSave` 在**发送时同步预留** `workspaceRevision + 1`，而不是等 ACK 才推进；
- `pauseWorkspacePersistence` 不再归零 revision。

## R2. B02：pagehide 与普通保存乱序，旧快照覆盖新快照

**根因**：后端是无版本 upsert，最终状态取决于哪个请求最后到库；`pagehide` keepalive 与普通 POST 可同时在途。

**修复**：实现服务端可验证的单调 revision（任务卡要求的方案）。

后端契约：

- `WorkspaceState` 增加 `revision: int = Field(default=0, ge=0)`；旧行缺失时 `read_revision()` 按 0 读取。
- `GET /api/v1/console/workspace` 返回当前 revision；客户端从该值继续。
- `_TaskStore.put_workspace` 在**同一把锁内**完成比较与写入：
  - `incoming > current`：接受；
  - `incoming < current`：抛 `WorkspaceRevisionConflict`（旧快照）；
  - `incoming == current` 且去除 `revision` / `updated_at` 后内容相同：幂等重放，返回现有状态；
  - `incoming == current` 但内容不同：抛 `WorkspaceRevisionConflict`（同版本内容不同），**不静默覆盖**；
  - 无历史行：作为首次写入接受。
- `_TaskStore.clear_workspace_task`（删除任务）与 `get_workspace_state` 的自愈幽灵指针分支属于服务端状态修改，`revision` 必须为当前值 + 1，避免客户端仍在途的旧 POST 把位置写回已删任务。
- 冲突映射为 `Result.fail(code=ErrorCode.STATE_CONFLICT.value, data={"conflict": True, ...})`；**只影响 UI 位置**，不改变 FSM、Artifact 或正式论文状态。

前端行为：

- 普通 POST 与 pagehide POST 携带**相同结构与 revision**；pagehide 同步预留更高 revision，使仍在途的普通保存注定被服务端拒绝。
- 初始化读取、默认页签激活、无变化重放**不伪造用户修改**：`loadWorkspaceState()` 成功后把服务端内容写入 `workspaceSaveGeneration.lastSnapshot` 作为基线，且持久化开关在恢复完成前保持关闭。
- 冲突时重新 `GET` 服务端状态，通过稳定 `aria-live` 区域提示“工作位置已在另一页面更新，请确认当前任务位置”，不自动用本地旧状态强行覆盖，也不循环 POST。

## R3. B03：横幅在任务状态变化后显示错误的下一动作

**根因**：`resumeSummaryCache` 只在初始化、身份切换或切换任务时更新；`resolveResumeForSelected` 在 `task_id` 匹配时直接返回旧缓存；`handleJobAction` 成功后只刷新 Job 列表。

**修复**：建立集中、无副作用的失效策略。

- 新增 `invalidateResumeSummary()`、`refreshVisibleResumeSummary()`、`syncResumeBannerWithJobs(jobs)`，不在各业务函数里复制清理逻辑。
- 成功状态变化后若横幅可见，强制 `GET /tasks/{id}/resume` 并重渲染，不命中旧缓存；如果返回失败或与当前任务不一致，立即隐藏横幅，绝不继续展示已知过期的数量与下一动作。
- `loadJobsPanel` 在渲染后比对活动作业集合，变化时触发刷新，覆盖轮询场景。
- 刷新摘要不执行环、不确认产物、不重试 Job、不调用模型。
- 失败操作不刷新，不把原本准确的摘要伪装成成功状态（只在 `response.code === 0` 时刷新）。

已接入的入口：`runCurrentRing`、`runRingShow`、`confirmNextRing`、`rollbackRing`、环1候选题选择、环3文献筛选保存、`handleJobAction` 的 cancel/retry、分节生成 / 修订 / 审批 / 批量生成 / 批量批准、研究协议 / 论证图 / 结果账本审批与三个表单提交、项目记忆创建 / 批准 / 驳回、删除任务与切换任务。
