# HY3架构分析报告评审

## 结论

HY3报告对项目的主体架构判断基本准确，尤其是“保留确定性十环FSM、扩展环内有界Agent、补UI工程化/SSE/评测/公式/图片管线”具有参考价值。但报告是外部时点的快照，不能直接作为开发指令。

## 已核实且采纳

| 建议 | 核对结果 | 处理 |
| --- | --- | --- |
| 环内Agent仅在环6试点 | 准确 | 保留有界只读设计，后续扩展到其他环节 |
| UI单文件风险高 | 准确 | 第一步已完成：HTML/CSS/主运行时/项目记忆功能模块拆分；后续继续缩小`app.js` |
| 多SQLite、Alembic和PostgreSQL路径未收敛 | 准确 | 保留在R4，不把“安装了可选依赖”当作已生产化 |
| 缺SSE与评测集 | 准确 | 分别保留在R1.5和R5 |
| 公式、图片/题注/图表交叉引用不足 | 准确 | 继续作为R3成品验收门槛 |
| `guardrail/`空目录造成能力可发现性差 | 现象准确 | 护栏实际分布在evidence/research/security/DOCX；后续做文档聚合或删除误导空目录 |

## 已过时或不完整

1. **“项目记忆只有schema”已过时**：当前已完成`PROJECT_MEMORY`持久化版本、自动校验、作者审批、新旧版替代、前端管理以及环6 Agent/章节提示强制消费。
2. **“多Provider是当前最高优先级”不符合已确认范围**：项目所有者已明确“先只支持DeepSeek，后续再增加多模型”。单供应商是阶段性产品决策，不是当前缺陷。
3. **“知识库三页签”等UI数量描述不是当前真实状态**：工作台已包含文献、记忆、证据、研究、分节、作业、笔记和图谱。
4. **“可选PostgreSQL”不等于迁移已落地**：当前仅有目标设计与依赖分层，没有正式Alembic基线和生产迁移演练。

## 明确不采纳

1. **现阶段不实施多Provider路由**：保持DeepSeek-only，等单链路评测与产品交付稳定后再做接口抽象。
2. **不向模型暴露直接写库/覆盖正文的通用可写工具**：Agent可生成候选草稿或变更建议，但真正落库必须由宿主校验、生成新版本并经HITL审批，不允许模型原地修改数据。
3. **不为“配置化”破坏确定性外轨**：不把十环FSM改成模型自由选路。未来如支持多论文类型，应使用经验证的类型化子流程，而不是开放式跳环。

## 经本次评审后的优先顺序

1. 先完成当前项目记忆阶段并扩展到其他有界Agent。
2. 在继续增加大型前端功能前，按`DESIGN.md`拆分单文件UI，保持现有视觉身份。
3. 建立引用真实性、证据覆盖和提示词回归评测集。
4. 推进SSE与变更级HITL，再做公式、图片和学校样式差异诊断。
