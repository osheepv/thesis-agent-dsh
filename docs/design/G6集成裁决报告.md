**裁决**：以系统设计 **M1~M9** 为权威编号（应用落地层，与 §2.1 业务域、§3.2 单模块五段式一一对应）。建立如下映射：

| 功能归属 | 业务能力层（高层架构 §5.1 / UserStory §2.1） | 应用落地层（系统设计 §3.2，权威） | 说明 |

| FSM 编排 | M1 | M1 | 十环节状态机 + 学位路由 + 回退 |
| 环节执行体 | M2 | M2 | 10 环节执行体（四字段输出） |
| 敏感环节 HITL 网关 | M3 | M3 | 环节 2/4/8/10 人工确认 |
| 状态存储 | — | **M4** | FSM 状态 / 回退栈 / 内容产物持久化（仅系统设计） |
| docx 模板解析 | M6（合并） | **M5** | 模板骨架解析 / 占位符提取 |
| docx 生成与校验 | M6（合并） | **M6** | docxtpl 生成 / openxml-audit 校验 |
| 万方工具 | — | **M7** | 万方取数 / 可信边界 / 降级（仅系统设计，语义易混淆） |

## 三、C2 REQ-KB 表名裁决

**背景**：UserStory §1.4 用单表 `t_knowledge_base`（标注"候选"）；系统设计 §1.3 / §4.2.15~4.2.18 拆为 `kb_*` 四张表（最终表结构）。

**裁决**：**以系统设计 `kb_*` 四表为权威结构**；UserStory 的 `t_knowledge_base` 仅视为早期候选命名，不作为实现依据。权威表结构：

| 表名 | 用途 |
|---|---|
| `kb_bound_session` | 会话绑定关系（REQ-KB 生命周期绑定） |
| `kb_entity` | 知识库实体（文献/笔记等，含 GIN 全文检索 `content_tsv`） |
| `kb_edge` | 实体双链关系（对标 Obsidian 双向链接） |
| `kb_snapshot` | 知识库版本快照 |

## 五、术语一致性确认（核心基线，全部一致）

以下核心业务基线在五份文档间**完全一致**，无冲突：

- 系统名称：基于 DeepSeek-Harness 的学位论文全流程写作 Agent（UserStory/安全设计为描述性简写，不必改）。
- 十环节：选题→新颖度评估→文献调研→文献综述→大纲→撰写→修改润色→引用校验→排版→定稿（环1~环10）。
- 敏感 HITL 环节：**环 2 / 4 / 8 / 10**（其余 6 环节全自动）。
- 密码基线：**最小 12 位**（大小写 + 数字 + 特殊字符）。
- SLA：P95 ≤ 3000ms；P99 ≤ 3000ms（敏感环节 HITL P99 ≤ 3s）。
- 容灾：RTO ≤ 30min；**RPO ≤ 6h**。
- 万方配额：日 2000 / 月 50000。
- docx 模板校验：扩展名 .docx 白名单 + 魔数 + ≤ 50MB + 随机重命名。
- RBAC0：writer / reviewer / manager。
- 会话绑定式隔离：session_id 强绑定，跨会话禁访问（仅手动挂载开放）。
- 演进轨：M0 本地单机桌面化（后续 Tauri 套壳）/ M1 私有化单机局域网 / M2 云端 SaaS 仅作蓝图。
- 万方三条可信边界：50 篇上限 / 没查到分两种 / 学科无名字。
