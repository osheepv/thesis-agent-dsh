# 全栈与产品审查报告评审

## 总结论

外部报告的主判断具有较高参考价值（约 8/10）：项目仍是受控试用级原型，真正护城河是证据可追溯、失败可见和逐阶段 HITL，而不是更强的自主写稿。其“先让通过一词在学术上诚实”的优先级判断成立。

报告不应直接当作 90 天实施计划。付费全文复跑应位于评测标准之后，否则只会再得到一个昂贵个案。

## 采纳

1. **学术通过分档**：结构、题录/元数据、正文证据和作者复核必须独立展示，不得共用一颗绿灯。
2. **评测先于复跑**：先建文献纳入/排除、论断—摘录和伪引/越界引用评测集，再重跑本科全文。
3. **对象工作台优于聊天日志**：对话保留为辅助，选题、文献、大纲、分节和证据应成为主操作面。
4. **继续收敛巨石**：前端按小接口迁移作业/研究/分节；后端把记忆、证据、研究、分节与 Job 查询从编排命令面拆出。
5. **错误契约和异常脱敏**：继续保留 `Result` 信封，但 HTTP 应正确区分 4xx/409/422/5xx，不回传原始异常。
6. **本地优先产品形态**：不先强制 PostgreSQL；应先收敛为单一事务 SQLite，再把 PostgreSQL 作为实验室部署选项。

## 需要修正的表述

- 作业面板已有 Token/费用上限和实时用量；缺失的是调用前预估、任务累计和“单价未配置”的明确提醒，不是完全没有预算仪表。
- 确认链已有 FSM Outbox 重放，Job 已有租约回收与幂等处理；应扩展现有恢复机制覆盖跨库对账，不是从零再造平行恢复。
- README 推荐命令已绑定 `127.0.0.1`；`0.0.0.0` 风险主要来自直接运行入口或试用配置，应统一默认值。
- 证据摘录只有审批状态，没有不可变版本；不应和项目记忆/论证图/结果账本统称为“版本 + 审批”。

## 报告遗漏但已核实的问题

1. 知识库原始数据、代码、日志和图片原可被环 3 当成文献，并无条件标为 `verified`。
2. 作者批准一条摘录原会把来源升为 `CONTENT_VERIFIED`，但系统并没有把摘录与上传全文逐字核对。
3. 项目记忆审批已使用认证会话身份，但证据、分节、论证图、研究协议和结果账本的 `actor` 仍可由请求体传入。
4. 删除任务跨多库和文件树顺序执行，中途失败可能留下半删除状态。

## 本次立即落地

- 环 3 只接受 `metadata.kind=literature` 的知识库文件，且用户上传默认 `uncertain` 而非 `verified`。
- 作者批准摘录不再自动把来源标为 `CONTENT_VERIFIED`。
- 环 8 产物增加结构/题录与元数据/正文证据三档派生结果，作者复核独立记录。
- 前端环 8 卡、历史摘要、证据面板和阶段条不再用同一绿色“已通过”混淆语义。

## 下一步

建立最小评测集，顺序为：文献纳入/排除 → 论断—摘录支撑/不支撑 → 伪引/页码越界 → 提示词约束回归。评测标准冻结后，再使用硬 Token 预算重跑本科全文。
